# 失误点、错误与经验

按「现象 → 原因 → 处理 → 教训」记录。供以后遇到同类问题快速定位。

---

## 一、环境类

### 1.1 `docker CLI not found`

**现象**

```
isolis> init
llm: monkeycode-basic/deepseek-flash via mc-direct (key ok len 36 prefix d23...)
error: docker CLI not found (install Docker and retry)
```

**原因**：工作区从未安装 Docker。`isolis.py` 的 `docker_bin()` 用
`shutil.which("docker")`，找不到就抛错。

**处理**

```bash
DEBIAN_FRONTEND=noninteractive apt-get install -y docker.io
```

装完后 CLI 和 dockerd 都在，但 `invoke-rc.d: policy-rc.d denied execution of start`
说明系统策略禁止服务自启，必须手动启动 daemon。

**教训**：`apt install` 成功不等于 Docker 可用。要分别验证 `docker --version` 和
`docker info`（后者需要 daemon）。

---

### 1.2 daemon 没起来

**现象**：`docker info` 报连不上 socket。

**处理**

```bash
dockerd --host=unix:///var/run/docker.sock \
        --storage-driver=overlay2 \
        --iptables=true
```

放后台终端运行，不要用 `&`（会话结束会被杀）。

**教训**：规则要求长时间运行的进程用受管理的后台终端。`&` 启动的进程在 shell
退出时可能被回收。

---

### 1.3 Docker Hub 不可达

**现象**：`docker build` 卡在 `FROM python:3.12-slim-bookworm`，
报 `TLS handshake timeout`。

**处理**：写镜像源。

```json
{"registry-mirrors": ["https://docker.m.daocloud.io"]}
```

写入 `/etc/docker/daemon.json` 后必须重启 daemon 才生效。

**教训**：`isolis.py` 的 `ensure_registry_mirror()` 会先探测 Hub（`registry-1.docker.io/v2/`），
只有不可达且未配置时才写 mirror。这个逻辑是对的，可以直接复用：

```bash
python3 -c "import isolis; print(isolis.ensure_registry_mirror())"
```

---

### 1.4 strict 镜像不存在导致 `docker run` 拉取超时

**现象**：验证 strict 容器时报

```
Unable to find image 'isolis-agent:strict-c2ba43eb87' locally
docker: Error response from daemon: Get "https://registry-1.docker.io/v2/": TLS handshake timeout.
```

**原因**：两个 profile 的 tag 不同，只构建了 tooled，strict 触发了从 Hub 拉取
同名镜像（实际不存在）。

**处理**：补建 strict。

```bash
docker build -t isolis-agent:strict-c2ba43eb87 agent
```

因 Dockerfile 相同，全部命中缓存，几秒完成。

**教训**：`isolis.py init` 会自己构建需要的 tag，但手工 `docker run` 验证时
要记得先把两个 tag 都建好。

---

### 1.5 MCP shell 没有 `MCAI_LLM_*`

**现象**：`python3 isolis.py setup` 报

```
error: MonkeyCode LLM was not injected: MCAI_LLM_BASE_URL and MCAI_LLM_API_KEY are required
```

**原因**：平台只把 LLM 变量注入用户的 TUI 会话，不注入 Agent 执行命令的 shell。
这是**正确行为**，不是 bug，按规则也不能去别处找 Key。

**处理**：Docker 相关验证（镜像、网络、容器、HTTP）照常做；LLM 对话验证交给
用户在 `isolis>` 会话里执行 `init` / `chat`。

**教训**：区分「我能验证的」和「只有用户会话能验证的」。不要为了跑通而伪造 Key
或改指向别的网关。

---

### 1.6 `ssh-keygen` 缺失导致测试失败

**现象**

```
FileNotFoundError: [Errno 2] No such file or directory: 'ssh-keygen'
FAILED tests/test_publish.py::test_ensure_ssh_key_idempotent
```

**原因**：Cage 的 publish 测试要生成 SSH key，环境里没有 `openssh-client`。

**处理**

```bash
apt-get install -y openssh-client
```

**教训**：这是环境缺依赖，不是代码问题。第一次 `apt install openssh-client`
可能报「no installation candidate」，先 `apt-get update` 再装。

## 二、代码类

### 2.1 旧的 Dockerfile 测试与规格冲突

**现象**

```
FAILED tests/test_agent_server.py::test_dockerfile_has_no_android_or_jdk_and_pins_base
```

测试断言 Dockerfile **不得**包含 `android`、`openjdk`、`JAVA_HOME`，
而 Isolis 规格要求**必须**包含。二者直接矛盾。

**原因**：Cage 时代不需要 JDK/Android，测试固化了那个约束；Isolis 的
「真实开发能力」目标要求相反。

**处理**：改写测试为断言必需组件存在（`test_dockerfile_pins_base_and_ships_dev_toolchain`）。

**教训**：测试编码的是当时的契约。需求变更时，与规格冲突的测试要连测试一起改，
并写清为什么改。

---

### 2.2 Isolis 运行时是残缺的

**现象**：`/info` 报 `tools: []`，`history_turns` 永远 0，没有 `/history`，
没有协议协商，记忆只截断不压缩。

**原因**：`agent/server.py` 里 Isolis 块只实现了最小骨架，没有按规格落地。

**处理**：重写整块（约 800 行），保留 Cage 运行时并用 `ISOLIS_AGENT_NAME` 分流。

**教训**：当同一文件里有两套运行时，用环境变量做显式分流，函数和常量加前缀隔离，
避免互相污染。这样旧测试不受影响。

---

### 2.3 LangChain `@tool` 用函数名做工具名

**现象**：规格要求工具名叫 `run_command`，但函数叫 `isolis_run_command`，
`/info` 会报错名字。

**处理**：自定义装饰器。

```python
def _isolis_named_tool(name):
    def decorator(func):
        if HAS_LANGCHAIN:
            return tool(name)(func)
        wrapped = tool(func)
        wrapped.name = name
        return wrapped
    return decorator
```

**教训**：LangChain 的工具名默认取 `__name__`。要在不重命名内部函数的前提下
控制对外工具名，用带参数的 `tool(name)`。

---

### 2.4 压缩产生多个 `[compressed history]`

**现象**：早期实现每次压缩都 `insert(0, entry)`，多次压缩后历史里有多个 marker。

**原因**：没有先检测已有 marker。

**处理**：压缩前判断 `history[0]` 是否已是 marker，是则把它的内容作为
`prior` 传给摘要函数，然后原地覆盖：

```python
marker = history[0] if _isolis_marker(history[0]) else None
body = history[1:] if marker else history[:]
...
history[:] = [entry] + rest
```

**教训**：规格明确「at most one compression entry may exist」。用 `history[:] = ...`
原地替换，保证只有列表引用不变的情况下内容被整体改写。

---

### 2.5 最新一对被折叠

**现象**：极端预算下，压缩把最新一轮对话也压进摘要，用户刚说的话丢了。

**处理**：`eligible = len(body) - 2`，永远保留最后两条（user + assistant）。

**教训**：规格「newest pair never folded」是硬约束，边界要单独测。

---

### 2.6 `image_tag` 对同一目录算出不同 tag

**现象**：`source="local"` 与 `source="./agent"` 得到不同 tag，重复构建。

**处理**：哈希前先解析成绝对路径。

```python
resolved = os.path.abspath(source_dir(sanitize_source(source)))
digest = hashlib.sha256((profile + "\n" + resolved).encode()).hexdigest()[:10]
```

**教训**：凡是参与缓存的 key，都要先规范化（绝对路径、去尾斜杠、小写等）。

---

### 2.7 `USER nobody` 让 tooled 装包失败

**现象**：tooled profile 下 `apt-get install` 报权限错误。

**原因**：Dockerfile 里写死了 `USER nobody`，运行时 `--user 0:0` 虽然能覆盖，
但若镜像层已固化了属主，写系统目录仍会失败。

**处理**：删除 Dockerfile 的 `USER nobody`，用户身份完全交给运行时的
`--user`（strict → `nobody`，tooled → `0:0`）。

**教训**：镜像负责「提供能力」，运行时负责「限制身份」。不要在镜像里写死安全策略。

---

### 2.8 非快进 pull 直接失败

**现象**：agent 源仓库有本地提交时，`git pull --ff-only` 失败，整个 init 崩溃。

**处理**：改为打印 notice 并保留本地 clone。

**教训**：规格要求「non-ff reported, keep local」。破坏性操作（覆盖本地改动）
要降级成提示，不能静默丢失用户工作。

---

### 2.9 `.isolis/state.json` 脏字段导致崩溃

**现象**：手工编辑 state 后，`port` 变成字符串 `"18080"`，后续 `int` 比较出错。

**处理**：`load_state()` 逐字段校验并补默认值，非法字段丢弃，`current` 不在
agents 里时置 `None`。

**教训**：状态文件是外部输入。读入时做一次规范化，比在每个使用点防御更可靠。

---

## 三、流程类

### 3.1 Python 输出缓冲导致看不到构建进度

**现象**：后台跑 `python3 -c "isolis.build_image(...)"`，日志文件一直是 0 字节。

**原因**：Python 默认块缓冲标准输出，重定向到文件时不即时刷新。

**处理**：不依赖该日志，改用 Docker 侧观察：

```bash
docker ps -a --format '{{.Names}}\t{{.Status}}'
du -sh /var/lib/docker
```

**教训**：长任务要选对观察点。`docker build` 的中间容器状态和磁盘增长更真实。
需要即时输出时加 `python3 -u`。

---

### 3.2 首次构建耗时远超预期

**现象**：构建约 17 分钟，一度以为卡死。

**原因**：2 核 8G 机器上要装 JDK、构建工具、Node、下载 Chromium（约 1GB），
每个 apt 步骤都是新容器。

**教训**：构建前先估算（Playwright Chromium 是大头），设置足够的 timeout
（用的 3600000ms），并用磁盘增长判断是否还在推进。

---

### 3.3 后台终端与 `&` 的选择

**教训**：daemon、构建这类长任务必须用受管理的后台终端，便于：
- 查看输出文件
- 监控资源（CPU/内存峰值）
- 用 ID 精确终止，不误杀别的进程

---

### 3.4 保留了 Cage 运行时

**决定**：没有删掉 Cage 代码，而是用 `ISOLIS_AGENT_NAME` 分流。

**理由**：仓库里 80+ 测试依赖 Cage 运行时（`agent.Handler`、`run_chat`、
`solve_challenge` 等）。删掉会让测试全红，且不属于本次任务范围。

**代价**：`agent/server.py` 变长（约 2300 行），两套运行时共存。

**后续选项**：若确定不再需要 Cage，可以单独开任务剥离，并同步删除对应用例。
这一步需要用户确认。

## 四、快速排查表

| 现象 | 先查 | 命令 |
|---|---|---|
| docker CLI not found | 是否装了 docker.io | `command -v docker` |
| 连不上 daemon | daemon 是否在跑 | `docker info` |
| 拉镜像 TLS timeout | 镜像源 | `cat /etc/docker/daemon.json` |
| 构建卡住 | 磁盘/中间容器 | `du -sh /var/lib/docker`; `docker ps -a` |
| LLM not injected | 是否在用户 TUI 会话 | `echo ${MCAI_LLM_API_KEY:+set}` |
| agent 启动失败 | 容器日志最后一行 | `docker logs isolis-<name>` |
| 端口冲突 | 谁占了 18080 | `ss -ltnp \| grep 1808` |
| strict 装包被拒 | profile 是否为 strict | `curl .../info` |
| 测试缺 ssh-keygen | openssh-client | `apt-get install -y openssh-client` |

## 五、绝对不要做的事

1. 不要为了跑通而伪造或复用别处的 `MCAI_LLM_API_KEY`。缺注入就如实报错。
2. 不要修改规格文件 `ISOLIS_PROMPT.md` 去迁就代码。代码要对齐规格。
3. 不要在 Dockerfile 里写死安全策略（`USER`、大范围 cap）。身份由运行时决定。
4. 不要用 `--privileged` 或挂载 Docker socket 来「解决」权限问题。
5. 不要用 `pkill`/`killall` 停后台进程，用终端 ID 精确终止。
6. 不要把镜像源写进版本库。它是本环境的临时适配，Hub 可达时不该存在。
